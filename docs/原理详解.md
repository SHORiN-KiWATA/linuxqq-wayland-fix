## 1. 它是什么

一个 `LD_PRELOAD` 注入库 `libqq-wl-portal.so`，加一个启动脚本 `linuxqq-wayland-fix`。

作用：让 QQ **自带的** Wayland 屏幕采集代码真正工作起来。QQ 里本来就有一套基于 portal + PipeWire 的采集实现，但缺一个「共享源选择器」，从来没被启用。本库替 QQ 补上这个选择器。

效果：

- 点共享 → QQ 自己的选窗 → niri 弹出 portal 选择框 → 对方看到画面；
- 画面数据直接从 niri 经 PipeWire 进入 QQ 的采集线程，不再像「截屏中转」类方案（如 qq-wayland-screenshare）那样在进程之间整帧搬运；
- QQ 主进程 CPU 从 70~96% 降到约 4%。

## 2. 背景：QQ 里那套没接上线的 Wayland 共享

### 2.1 QQ 屏幕共享的结构

```
QQ 主进程（Electron 界面，wrapper.node）
 └─ ppapi 子进程（音视频插件）
     ├─ libAVSDKPlugin.so   ← 音视频 SDK：会话、编码、网络。它决定「共享哪个屏幕」
     └─ broadcast-core.so   ← 采集库：真正去拿屏幕画面
```

`broadcast-core.so` 位于 `~/.config/QQ/versions/<版本>/avsdk/`，由 `libAVSDKPlugin.so` 用 `dlopen(..., RTLD_NOW)` 加载（没有 `RTLD_DEEPBIND`，所以 `LD_PRELOAD` 能拦到它调用的函数）。

### 2.2 broadcast-core 里的两条采集路径

反汇编 `broadcast-core.so` 后得到下面这些事实，地址对应 3.2.34：

**判断函数** `IsWayland`（0x5c9d0）：

```c
int IsWayland(void) {
    const char *t = getenv("XDG_SESSION_TYPE");
    return t && strcmp(t, "wayland") == 0;
}
```

**入口** `MonitorCapture_CaptureDisplay`（0x510a0）：

```c
if (IsWayland()) {
    uint64_t h = capture->handle;            // 上层传来的 64 位「显示器句柄」
    capture->pw_fd   = (uint32_t)h;          // 低 32 位 → +0x1f0
    capture->pw_node = (uint32_t)(h >> 32);  // 高 32 位 → +0x200
    启动线程 MonitorCapture_WaylandProc;
} else {
    启动线程 MonitorCapture_X11Proc;          // XShmGetImage / XGetImage 截根窗口
}
```

**Wayland 采集线程** `MonitorCapture_WaylandProc`（0x51210）：

1. 用自家的 `DllGetFuncByName` 加载 `libpipewire-0.3.so`，然后**用 `dlsym` 逐个取出 21 个 `pw_*` 函数**放进函数表（`pw_init`、`pw_context_connect_fd`、`pw_stream_connect`……）；
2. `pw_context_connect_fd(ctx, capture->pw_fd, ...)` 连上 portal 给的 PipeWire 远端；
3. `pw_stream_connect(stream, INPUT, capture->pw_node, ...)` 连上那路画面；
4. 在 `OnStreamProcess` 回调里取帧 → 上传 OpenGL 纹理 → 交给编码。

**本该负责填句柄的选择器** `CaptureSelector_DoModal` / `CreateProc` / `StartProc`：里面有完整的 portal 调用（`CreateSession`、`SelectSources`、`Start`、`OpenPipeWireRemote`），拿到 fd 和 node id 后打包成句柄。

### 2.3 断在哪里

- **没有任何代码调用 `CaptureSelector`**：broadcast-core 内部没有引用，`libAVSDKPlugin.so` 里也找不到相关字符串。
- 上层（`libAVSDKPlugin.so`）在 Wayland 下直接拒绝：`IsScreenShareEnvAvailable` 用它自己的 `util::IsWayland()`（同样是看 `XDG_SESSION_TYPE`）判断，界面就弹出「Wayland桌面环境暂时无法使用屏幕分享功能」。
- 就算绕过界面，上层传给 broadcast-core 的也是 X11 显示器编号（实测为 `1`）。Wayland 分支会把它当成「fd=1、node=0」去连 PipeWire，什么也连不上。

结论：**采集这一半已经写好，选择器那一半没接上线。**

## 3. 工作原理

### 3.1 三处拦截

| # | 拦截什么 | 仅对谁生效 | 做什么 |
| --- | --- | --- | --- |
| 1 | `getenv("XDG_SESSION_TYPE")` | 调用方在 `broadcast-core.so` 里 | 返回 `"wayland"`，让它走 Wayland 分支。QQ 其余部分仍看到 `x11`，界面不拦截 |
| 2 | `dlsym(handle, "pw_...")` | 调用方在 `broadcast-core.so` 里 | 取 `pw_context_connect_fd` / `pw_stream_connect` / `pw_core_disconnect` 时，返回本库的包装函数 |
| 3 | 上面三个包装函数 | — | 自己走一遍 portal，把真的 fd、node id 换进去；结束时关闭 portal 会话 |
| 4 | `pa_context_get_sink_info_by_name` / `pa_context_get_source_info_by_name` | 调用方在 `broadcast-core.so` 里 | 把设备采样格式改报为 FLOAT32LE，让「共享设备音频」能启动（见 3½ 节） |

### 3.2 一次完整的共享

```
用户点「确定」
  │
  ▼
libAVSDKPlugin（以为是 X11）→ 把显示器编号 1 作为句柄交给 broadcast-core
  │
  ▼
broadcast-core: IsWayland()
  └─ getenv("XDG_SESSION_TYPE") ──拦截①──→ "wayland"
  │
  ▼
MonitorCapture_WaylandProc
  ├─ dlsym("pw_context_connect_fd") ──拦截②──→ wrap_connect_fd
  ├─ dlsym("pw_stream_connect")     ──拦截②──→ wrap_stream_connect
  ├─ dlsym("pw_core_disconnect")    ──拦截②──→ wrap_core_disconnect
  │
  ├─ wrap_connect_fd(ctx, fd=1)  ──③──┐
  │     丢弃 fd=1（它不是 fd！）        │
  │     CreateSession                  │
  │     SelectSources（屏幕+窗口）      │   D-Bus → xdg-desktop-portal → niri
  │     Start ──→ niri 弹出选择框，用户选 │
  │     OpenPipeWireRemote → 真 fd      │
  │     真 pw_context_connect_fd(真 fd) ◄┘
  │
  ├─ wrap_stream_connect(target=0) → 换成 Start 返回的 node id → 真 pw_stream_connect
  │
  ├─ （之后完全是 QQ 自己的代码：收帧 → GL → 编码 → 发送）
  │
  └─ 共享结束：wrap_core_disconnect → 真 pw_core_disconnect → Session.Close
```

### 3.3 为什么拦 `dlsym` 而不是直接定义同名的 `pw_*` 函数

broadcast-core 是先 `dlopen("libpipewire-0.3.so")`，再 `dlsym(那个句柄, 名字)`。用句柄查找只搜那个库和它的依赖，**不搜 LD_PRELOAD 的库**，所以直接定义 `pw_context_connect_fd` 不会生效，只能在 `dlsym` 这一层截。

## 3½. 共享电脑声音（设备音频）

### 现象

共享工具栏点了「共享设备音频」，对方仍然听不到电脑里播放的声音；界面上没有任何报错。

### 排查过程

用 `gdb` 在 ppapi 进程里挂只打印、不暂停的探针（`dprintf`），观察切换按钮时的调用：

```
ConfigureShareAudio(…, enable=1)       ← 界面命令到了
EnableShareAudio(enable=1, 2, 48000, 16)
InitAudioCapture enter
  bc AudioMixer_Init
  bc AudioCapture_Init                 ← broadcast-core 的系统声音采集
  bc AudioCapture_EnumDevice           ← 找默认输出设备
  audio_capture_->Init returned 0x80004001   ← E_NOTIMPL
  EXIT: audio_capture_ init fail
EnableShareAudio(enable=0, …)          ← QQ 悄悄把它关掉了
```

### 原因

反汇编 `AudioCapture_Init`（broadcast-core，0x4af60）：

```c
查询默认输出设备的 sample_spec → format, rate, channels
if (format == 0 || rate == 0)               return E_NOTIMPL;
if (format != PA_SAMPLE_S16LE /*3*/ &&
    format != PA_SAMPLE_FLOAT32LE /*5*/)    return E_NOTIMPL;
// 然后按同样的格式 pa_stream_connect_record 录这个设备的 .monitor
```

QQ 只支持 16 位整数或 32 位浮点格式的输出设备。很多板载声卡（ALSA 设备）的原生格式是 **s32le**（格式 7），于是直接失败。这和 Wayland 无关，「截屏中转」类方案下同样存在。

### 修法

拦截 broadcast-core 调用的 `pa_context_get_sink_info_by_name` / `pa_context_get_source_info_by_name`，在结果回调里把 `sample_spec.format` 改成 FLOAT32LE 再交给 QQ。QQ 随后按 FLOAT32LE 去录 `.monitor`；**录音端可以要求任意格式，PipeWire 会自动转换**，所以对声音没有影响。

实现上的两个坑：

1. **回调要包一层**：原回调和原 userdata 存进一个小结构，用自己的 trampoline 回调，复制一份 `pa_sink_info`、改格式后再调用原回调；`eol` 时释放。
2. **真函数要从 libpulse 里直接取**：libpulse 是作为 broadcast-core 的依赖被 `dlopen` 进来的（局部作用域），`dlsym(RTLD_NEXT, …)` 找不到它，返回 NULL，一调用就崩。改成 `dlopen("libpulse.so.0", RTLD_NOLOAD)` 再 `dlsym`。本库也不链接 libpulse，不会给其它进程增加依赖。

正常时日志里会出现：

```
device audio: report sample format 7 as float32le (5) to broadcast-core
```

如果你的输出设备本来就是 s16le / f32le，这行不会出现，也不需要它。

## 4. 代码逐段讲解

### 4.1 判断调用方

```c
static int from_broadcast_core(const void *caller)
{
    Dl_info info;
    if (!dladdr(caller, &info) || !info.dli_fname) return 0;
    const char *base = strrchr(info.dli_fname, '/');
    return !strcmp(base ? base + 1 : info.dli_fname, "broadcast-core.so");
}
```

- `__builtin_return_address(0)` 拿到「谁调用了我」的代码地址；
- `dladdr` 查这个地址属于哪个 `.so`；
- 只认 `broadcast-core.so`，其它库的调用一律原样放行。

`dlsym` 的情况：broadcast-core 里的 `XGetProcAddress` 是一条 `jmp dlsym@plt`（尾跳转），所以 `dlsym` 看到的返回地址落在 broadcast-core 的 `DllGetFuncByName` 里，判断成立。

### 4.2 getenv

```c
char *getenv(const char *name)
{
    if (name && !strcmp(name, "XDG_SESSION_TYPE") &&
        from_broadcast_core(__builtin_return_address(0)))
        return (char *)"wayland";
    return name ? lookup_env(name) : NULL;
}
```

`lookup_env` 自己遍历 `environ`，不再转发给 glibc 的 `getenv`，避免任何递归或初始化顺序问题。

### 4.3 dlsym 与 musttail

```c
void *dlsym(void *handle, const char *name)
{
    if (!real_dlsym) resolve_dlsym();
    if (name && !strncmp(name, "pw_", 3) &&
        from_broadcast_core(__builtin_return_address(0)))
        return intercept(handle, name);
    __attribute__((musttail)) return real_dlsym(handle, name);
}
```

要点：

- **真 dlsym 从哪来**：`dlvsym(RTLD_NEXT, "dlsym", "GLIBC_2.34")`（找不到就退回 `GLIBC_2.2.5`）。`dlvsym` 没被拦截，所以不会递归。
- **为什么懒加载**：其它库的构造函数可能比本库的构造函数更早调用 `dlsym`。
- **为什么必须尾调用**：glibc 的 `dlsym` 用返回地址判断调用者是谁，`dlsym(RTLD_NEXT, ...)` 的语义就靠它。如果写成普通调用，glibc 会以为调用者是本库，别的库的 `RTLD_NEXT` 查找就会出错。`musttail` 强制编译成 `jmp`，栈上的返回地址仍然是原调用者。编译后可用 `objdump -d libqq-wl-portal.so | awk '/<dlsym>:/,/^$/'` 确认里面有 `jmp *%rdx`。GCC 15 起支持 `musttail`。

### 4.4 portal 请求的通用函数 `portal_request`

portal 的 `CreateSession` / `SelectSources` / `Start` 都是异步的：方法本身立即返回一个 Request 对象路径，真正的结果稍后通过该路径上的 `Response` 信号送来。

做法：

1. 自己生成 `handle_token`，按规范预测出 Request 路径：
   `/org/freedesktop/portal/desktop/request/<发送者唯一名，去掉冒号、点换成下划线>/<token>`；
2. **先订阅**这个路径的 `Response` 信号，**再调用**方法，避免信号先到而错过；
3. 在一个**本线程私有的 `GMainContext`** 里跑循环等待，不干扰 QQ 自己的事件循环；
4. 带超时：`Start` 等 300 秒（给用户在弹框里慢慢选），其余 30 秒；
5. `response` 为 0 表示成功，1 表示用户取消，2 表示其他失败。

### 4.5 `run_portal`：完整流程

| 步骤 | 方法 | 关键参数 | 取回 |
| --- | --- | --- | --- |
| 1 | `CreateSession` | `session_handle_token` | `session_handle` |
| 2 | `SelectSources` | `types=3`（屏幕+窗口）、`multiple=false`、`cursor_mode` | — |
| 3 | `Start` | parent_window `""` | `streams` 数组，取第一个的 node id |
| 4 | `OpenPipeWireRemote` | — | 通过 Unix fd 列表传回的 PipeWire fd |

`cursor_mode`：先读 `AvailableCursorModes` 属性（niri 返回 7），支持就用 2（光标画进画面），否则用 1（隐藏）。

### 4.6 D-Bus 连接必须常驻（踩过的坑）

```c
static GDBusConnection *bus(void)   // 进程内常驻一份 session bus 连接
```

**portal 会话绑定在发起请求的 D-Bus 连接上**，这条连接一断，portal 就认为请求方退出了，会立即收回会话。

第一版用 `g_bus_get_sync()` 拿到共享连接，用完就 `g_object_unref()`。ppapi 进程里没有别人持有这条连接，引用计数归零，连接随即关闭。结果是：niri 刚交出 node（日志 `delivering node id 195`），3 毫秒后就 `stop_cast`，QQ 的输入流一直处于 `suspended`，对方一直「正在加载」。

现在 `bus()` 在整个进程生命周期内持有连接，断了会自动重连。

### 4.7 三个包装函数

**`wrap_connect_fd`**

- 收到的 `fd` 其实是 X11 显示器编号的低 32 位（实测为 1），**绝不能交给 PipeWire**。`pw_context_connect_fd` 会接管这个 fd 并在结束时关掉它，传进去 1 就等于把进程的 stdout 关了。
- 跑 `run_portal()`，成功就用真 fd 调用真函数；
- 失败或用户取消时，创建一对 `socketpair`，关掉一端，把另一端交给 PipeWire。这样连接必然失败，QQ 走它自己的失败路径，不会崩；
- 记下 `active_core`、`active_session`、`active_node`。

**`wrap_stream_connect`**

- 把 `target_id`（实测为 0）换成 `active_node`。

**`wrap_core_disconnect`**

- 如果断开的是我们记录的那个 core，就清空状态，先调用真函数，再对 portal 会话调用 `Session.Close`。niri 收到后停止录屏。

## 5. 部署

见 [README](../README.md#安装)。安装后的文件：

| 路径 | 内容 |
| --- | --- |
| `/usr/bin/linuxqq-wayland-fix` | 启动脚本（含 `--doctor` 自检） |
| `/usr/lib/linuxqq-wayland-fix/libqq-wl-portal.so`（Fedora 为 `/usr/lib64/...`） | 注入库 |
| `/usr/share/applications/linuxqq-wayland-fix.desktop` | 应用菜单入口「QQ（Wayland修复版）」 |

启动脚本做的事：

| 设置 | 作用 |
| --- | --- |
| `LD_PRELOAD=…/libqq-wl-portal.so` | 注入本库 |
| `XDG_SESSION_TYPE=x11` | 让 QQ 界面和 libAVSDKPlugin 不拦截共享。broadcast-core 那边由本库单独改成 `wayland` |
| `MESA_SHADER_CACHE_DISABLE=true` | 绕开 QQ 自带 zstd 与 Mesa 的符号冲突（见 §7.4）。Wayland 路径同样会初始化 OpenGL，同样需要 |
| `--ozone-platform=x11`（默认） | QQ 界面走 XWayland，与共享无关。共享时的悬浮工具栏/参会者面板是普通顶层窗口，Wayland 不允许客户端给顶层窗口定位，合成器会乱摆；X11 的位置提示多数 WM 会采纳，工具栏才能顶部居中。可用 `QQ_WAYLAND_FIX_OZONE=wayland` 换回原生 Wayland 界面 |

### 关于 musttail 与汇编蹦床

最初的实现用 `__attribute__((musttail))` 让 `dlsym` 的转发成为尾调用，但这需要 GCC 15+。为了能在 Debian 12（GCC 12）和 Ubuntu 24.04（GCC 13）上编译，现在 x86_64 和 aarch64 改用汇编蹦床（`src/dlsym_trampoline.S`）：先调用 C 函数 `qqwl_dlsym_decide()` 判断要不要拦截，不拦截就恢复参数，再 `jmp` 到真正的 dlsym。其它架构仍然走 musttail。

## 6. 使用

1. **完全退出 QQ**，托盘里也要退出。检查：`pgrep -af '^/opt/QQ/qq --ozone'` 没有输出。
2. **Easy Effects 可以照常运行**，但它的排除名单里必须有 `TRAE`，QQ 麦克风选 **Easy Effects Source**（见 §7.4）。
3. 运行 `linuxqq-wayland-fix`。
4. 发起共享。QQ 先弹出**它自己的**选窗，随便选「桌面1」，点「确定」。这一步选什么不影响结果。
5. **niri 的选择框**弹出来，在这里选真正要共享的屏幕或窗口。
6. 全屏蓝框会出现并挡住屏幕。这是 QQ 为 X11 设计的覆盖层，本方案暂未处理。可以在 niri 里把它移到别的工作区，或者让它保持浮动。
7. 结束共享后，portal 会话会自动关闭。

想更流畅：第 5 步选单个窗口，别选整个屏幕。

## 7. 验证与排错

### 7.1 正常时的日志

```bash
grep qq-wl-portal "$XDG_RUNTIME_DIR/linuxqq-wayland-fix.log" | tail
```

```
[qq-wl-portal pid=3366112] broadcast-core asked to connect fd=1, opening portal
[qq-wl-portal pid=3366112] portal ok: pipewire fd=82 node=127
[qq-wl-portal pid=3366112] stream connect target 0 -> 127
[qq-wl-portal pid=3366112] device audio: report sample format 7 as float32le (5) to broadcast-core   ← 打开「共享设备音频」时
...（结束共享时）
[qq-wl-portal pid=3366112] share ended, portal session closed
```

### 7.2 检查 QQ 的视频流是否在跑

```bash
pw-dump | python3 -c '
import json,sys
for o in json.load(sys.stdin):
  i=o.get("info") or {}; p=i.get("props") or {}
  if p.get("node.name")=="qq" and "Video" in str(p.get("media.class")):
    print(o["id"], i.get("state"), (i.get("params") or {}).get("Format"))'
```

正常：`running`，格式类似 `BGRx 2560x1440`。如果是 `suspended` 并且 `Format []`，说明没收到画面。

### 7.3 检查 niri 有没有提前停止

```bash
journalctl --user --since '-5min' -o cat | grep -E 'delivering node id|stop_cast|StartCast'
```

`delivering node id N` 之后紧接着出现 `stop_cast`，说明 portal 会话被收回了，通常是 D-Bus 连接断了（见 4.6）。

### 7.4 症状对照表

| 症状 | 原因 | 办法 |
| --- | --- | --- |

### 7.4 QQ 自身的两个崩溃（与 Wayland 无关）

**Mesa 着色器缓存与 QQ 自带 zstd 冲突**：QQ 的 `libAVSDKPlugin.so` 静态打包并导出了 221 个 `ZSTD_*` 符号。共享时 broadcast-core 初始化 OpenGL，Mesa 读磁盘着色器缓存调用系统 libzstd，libzstd 内部经 PLT 的调用被 QQ 的同名符号截走，结构体不兼容，采集进程 SIGTRAP。调用栈：`VSync_Proc → glXChooseVisual → libgallium → libzstd ZSTD_decompress → libAVSDKPlugin ZSTD_decompressDCtx`。解决：`MESA_SHADER_CACHE_DISABLE=true`。

**Easy Effects 移动音频流引发竞态**：Easy Effects 会把新出现的流移到自己的设备上。QQ 音频模块收到「流被移动」后在采集线程里调用 `OnDefaultDeviceChanged` 重新枚举设备，与主线程的枚举并发。它枚举的写法是先把 `PulseAudioWrapper` 的成员指针（+0xe8 / +0xf8）指向调用方栈上的缓冲区，再等异步回调写入，两个线程同时这么做就会写坏内存，之后在 mars xlog 的 `realloc` 里被分配器检测到而 SIGTRAP。对照实验：Easy Effects 运行、虚拟设备存在，仅把 `TRAE` 加入它的输入/输出排除名单，即不再崩溃。解决：排除名单加 `TRAE`，QQ 麦克风选 Easy Effects Source。


### 7.5 共享窗口时画面斜切成条纹（QQ 的 bug，已修）

**现象**：共享单个窗口时，对方看到的画面挤在左侧，满是竖条纹、行重复。

**原因**：`OnStreamProcess`（broadcast-core 0x52af0）对共享内存帧：

```c
memcpy(pbo, buffer->datas[0].data, width * height * 4);   // 忽略 chunk->stride / offset
glTexSubImage2D(GL_TEXTURE_2D, 0, 0, 0, width, height, fmt, GL_UNSIGNED_BYTE, 0);
```

合成器给的每行常带填充（stride > width×4），宽度不规整的窗口尤其常见，于是逐行错位。DMA-BUF 分支会正确使用 stride，但 QQ 声明的格式里没有 modifier，合成器只会给共享内存帧。

**修法**：拦截 `pw_stream_add_listener`（额外挂一个监听器，从 `param_changed` 解析 `spa_video_info_raw` 得到宽高）、`pw_stream_dequeue_buffer`（帧有填充或偏移时重排成紧凑的一块，临时替换 `datas[0].data`）、`pw_stream_queue_buffer`（还帧前恢复原指针）、`pw_stream_destroy`（释放状态）。

**验证**：本地 PipeWire 生产者输出 1001×300、stride 4032 的帧，消费者放在名为 broadcast-core.so 的库里，按 QQ 的方式取帧并逐像素校验：不注入 0/90 帧正确，注入后 89/89 帧正确。

## 8. 它到底有多「原生」：还涉及哪些 X11

| 环节 | 用的是 | 说明 |
| --- | --- | --- |
| 画面采集（niri → PipeWire → QQ） | **Wayland** | 不调用任何 X11 截屏函数，也不需要 XShm |
| 选择共享源 | **Wayland portal** | 由本库替 QQ 发起 |
| QQ 主窗口 | X11 | 默认 `--ozone-platform=x11`，让共享悬浮工具栏/参会者面板能按 QQ 的意图定位（见 §5 设置表） |
| QQ 自己的选窗缩略图 | X11 | `wrapper.node` 用 `XGetImage` 截，所以 Wayland 窗口和桌面显示为黑 |
| 共享进程的其它部分 | X11 | 实测共享期间 ppapi 对 XWayland 开着 2 条连接。可能来源：`eglGetDisplay()` 没指定平台，Mesa 默认走 X11；libAVSDKPlugin 仍在 X11 模式下枚举显示器（未逐一确认） |
| QQ 的整体判断 | X11 | 全程以为是 X11 会话，全屏蓝框也是按 X11 的方式建的 |

结论：**画面这条路是原生 Wayland，但 QQ 仍然需要 XWayland 才能完成共享**，X 只是被用来做些杂活。要彻底去掉 X，需要腾讯在界面层正式支持 Wayland。

## 9. 性能

共享 2560×1440 桌面时实测：

| | QQ 主进程 | ppapi（其中编码线程） | niri |
| --- | --- | --- | --- |
| 截屏中转方案（qq-wayland-screenshare） | 70~96% | ~64%（~50%） | ~56% |
| **本项目** | **~4%** | ~56%（~49%） | ~60% |

- 省掉了截屏中转方案在主进程里收帧、以及每帧 14.7MB 的跨进程拷贝。
- **流畅度没有变化**：两种方案画面进入 QQ 之后的路是一样的，都要经过单线程软件 H.264 编码（`VideoEncoder` 线程约 50%）、QQ 自己的码率和帧率控制、网络。这一段我们改不了。
- QQ 声明能接受 0~1000fps，niri 实际按屏幕刷新率送帧（最高 180）。可以考虑在 `wrap_stream_connect` 里改写参数加上帧率上限，进一步减轻 niri 的负担，但对流畅度无益。

## 10. 已知限制

1. **全屏蓝框不会自动隐藏**。
2. **依赖 QQ 未正式启用的内部实现**：`IsWayland()` 的判断方式、句柄的打包格式、PipeWire 函数的获取方式（`dlsym` 加函数名）。任何一个变了都会失效，而且多半不报错，只是没画面。
3. **只在 QQ 3.2.34-53644 + niri 上验证过**。其它桌面环境（KDE、GNOME、wlroots 系）理论上能用，因为都是标准 portal，而且 QQ 不接受 DMA-BUF，portal 会退回普通内存画面。但没有实测过。
4. **同一时间只支持一路共享**（全局状态只有一份）。QQ 本身也只允许一路。
5. **QQ 自己的选窗是摆设**：选什么都一样，以 niri 弹框里的选择为准。
6. QQ 自身的两个崩溃问题靠外部设置绕开：Mesa zstd 冲突（`MESA_SHADER_CACHE_DISABLE=true`），以及 Easy Effects 移动音频流引起的竞态（排除名单加 `TRAE`）。

## 11. QQ 更新后怎么重新确认能不能用

QQ 会悄悄热更新到 `~/.config/QQ/versions/<新版本>/`。更新后如果不能用了，按顺序检查：

```bash
V=$(ls -d ~/.config/QQ/versions/*/ | sort -V | tail -1)
B=$V/avsdk/broadcast-core.so
objdump -d --no-show-raw-insn $B > /tmp/bc.s

# 1. Wayland 采集路径还在不在
strings -a $B | grep -E 'MonitorCapture_WaylandProc|OpenPipeWireRemote'

# 2. IsWayland 是否还是「getenv + strcmp」的写法
awk '/<IsWayland>:/,/ret/' /tmp/bc.s | grep -E 'getenv|strcmp'

# 3. 句柄拆分方式：应能看到「右移 32 位、存 node、存 fd」三条指令
awk '/<MonitorCapture_CaptureDisplay>:/,/WaylandProc/' /tmp/bc.s | grep -E 'shr +\$0x20|0x1f0|0x200'

# 4. PipeWire 函数是否仍经由 dlsym 获取
strings -a $B | grep -E '^pw_(context_connect_fd|stream_connect|core_disconnect)$'
awk '/<XGetProcAddress>:/,/ret|jmp/' /tmp/bc.s | grep dlsym

# 5. 加载方式有没有加上 RTLD_DEEPBIND（0x8）。加了就拦不到；正常应该是 mov $0x2,%esi
objdump -d --no-show-raw-insn $V/avsdk/libAVSDKPlugin.so | grep -B3 'dlopen@plt>$' | grep esi
```

全部符合，就重新测一次共享；有不符合的，对照第 2 节的分析改代码。

## 附：剪贴板修复（`libqq-clipbridge.so`）

### 问题在哪

QQ 在 Wayland 下有两套剪贴板路径：

- **Chromium 网页内核自己的 Ctrl+C / Ctrl+V**：走 Wayland，正常；
- **QQ 自己的剪贴板代码**：右键「复制」、粘贴图片和文件等。实现在 `wrapper.node` 的 `ClipBoardHelper` 里，只用 Xlib（`XSetSelectionOwner` / `XConvertSelection` / `XGetSelectionOwner`），没有任何 Wayland 分支，所以只读写 X11 剪贴板。

QQ 窗口是原生 Wayland 窗口，不是 X11 窗口，XWayland（或 xwayland-satellite）不会帮它同步 X11 剪贴板，于是两边互不相通。浏览器 Ctrl+C 后粘贴进 QQ「时好时坏」，就是因为 QQ 有时用 Chromium 的粘贴（读 Wayland），有时用自己的粘贴处理（读 X11）。

这些剪贴板调用由 `major.node` 在 C++ 层直接发起，不经过 JS 层，所以没法在 JS 层改成调用 Electron 的剪贴板模块。

### 怎么桥接

注入库在 QQ 主进程里起一个后台线程，持有**自己的** X 连接和 Wayland 连接：

- **QQ 复制 → Wayland**：拦截 `XSetSelectionOwner`。QQ 取得 CLIPBOARD 后，线程向 QQ 要 TARGETS，再通过 data-control 在 Wayland 上提供对应的 MIME 类型；别的程序粘贴时才向 QQ 取那一种格式的数据（支持 INCR 分块）。
  - 文本：X11 的 `UTF8_STRING` 等映射为 `text/plain;charset=utf-8` 等；
  - 文件：QQ 给的是裸路径，转成 `file://` URI（`text/uri-list` 用 CRLF 分隔），并提供 `x-special/gnome-copied-files`；此时不提供 `text/html`（QQ 的 HTML 只是 `<img src=缓存路径>`，很多程序会优先选它而拿不到图）；
  - 复制图片而原图没有下载到本地时（路径指向不存在的文件），只提供 `image/png` 数据。
- **Wayland → QQ 粘贴**：data-control 的 `selection` 事件一到，线程用自己的 X 窗口接管 CLIPBOARD 并声明对应的 X11 TARGETS；QQ 粘贴时按需从 Wayland 读取，大数据走 INCR 分块发给 QQ。`text/uri-list` 也以 `x-special/gnome-copied-files` 提供给 QQ。
- **防回环**：自己写到 Wayland 的内容附带私有格式 `application/x-qq-clipbridge`，收到带这个格式的 `selection` 时忽略；接管 X11 时，TARGETS 里也带上这个格式。
- **不抢 X11 程序的剪贴板**：X11 程序（如 Typora、CodeBuddy 这类跑在 XWayland 下的 Electron 程序）复制时，xwayland-satellite / KWin / wlroots 会把它同步到 Wayland（satellite 一次复制可能同步两次）。这次 Wayland 变化不能当成「别的程序复制了」去接管 X11，否则合成器又把我们同步回 Wayland，来回循环，大家都读不到内容。用 XFixes 记下每次 X11 程序（包括 QQ 自己）设置 CLIPBOARD 的时间，1.5 秒内、且它仍是主人时到来的 Wayland 变化都视为同步；格式里有 `TIMESTAMP` / `TARGETS` / `MULTIPLE` 这类 X11 才有的名字时也是。主人若是合成器自己的代理窗口（用 XRes 查出所属进程：合成器本身或 `xwayland-satellite`），照常接管。
- **已经是主人时不重复接管**：每次换主人，satellite、fcitx5、Steam 等监听 X11 剪贴板的程序都会来读，fcitx5 还会把文字写回 Wayland。已经持有 X11 剪贴板时只更新内容，不再 `SetSelectionOwner`，避免这种来回。
- **启动时**：连上 Wayland 会先收到一次「当前剪贴板」；如果此时 X11 剪贴板已经有主人（比如 QQ 刚复制过），不去抢。

### 协议与兼容

- 优先 `ext-data-control-v1`，没有时退回 `wlr-data-control-unstable-v1`。两者的请求和事件完全一致，只有创建对象（`create_data_source`、`get_data_device`）需要区分协议，其余调用共用一套代码。
- GNOME 两种都不支持，剪贴板修复在 GNOME 上不可用。
- QQ 以 X11 方式运行时（命令行最后一个 `--ozone-platform=` 为 `x11`，或没有该参数时 `--ozone-platform-hint` / `ELECTRON_OZONE_PLATFORM_HINT` 为 `x11`）不启用：此时 QQ 窗口是 X11 窗口，XWayland 自己会同步剪贴板。

### 与外部同步工具（如 linuxqq-clipsync）的比较

外部工具在**每次**剪贴板变化时都要把内容完整读出、再写到另一边（多次启动 xclip / wl-paste 等进程），且只能同步一种格式，同步完成前有空窗期。本库只在变化时交换格式列表，粘贴时才传数据、只传一次，保留全部格式，另一侧几乎立即可用，且只在 QQ 运行期间存在。

## 附：共享时防闪退（窗口几何为空）

显示器坐标不从 0 开始时（如 Hyprland 单屏 `position=1920x0`），点「确定」开始共享 QQ 会闪退（#1，由 [@YoungJurry](https://github.com/YoungJurry) 在 #2 中最早定位）。

崩溃点在 QQ 主程序里 Chromium 的 Wayland 后端：发 `xdg_surface.set_window_geometry(x, y, w, h)` 之前，它检查宽、高都不为 0，否则 `int3; ud2` 主动崩溃。坐标错位时 QQ 给共享相关的某个窗口算出了空的几何，就撞上这个检查。

不能简单去掉检查：把 0 尺寸发给合成器，wlroots 和 niri 都会按协议报错并断开 QQ（只有 Hyprland 容忍）。`libqq-wl-portal.so` 改的是崩溃桩：把 `int3; ud2` 改写为「弹掉栈上的一项、跳到函数自带的收尾代码」，几何为空时直接返回、不发这个请求，合成器按窗口内容决定大小。

- 只在 QQ 主进程（命令行没有 `--type=`）里做；
- 要求整个函数的字节都对得上（开头、两处检查、跳转目标、收尾代码、填充），且恰好匹配一处，否则不动 QQ、只记日志；
- `--doctor` 会检查 QQ 本体里这段代码还在不在；`QQ_WL_GEOMETRY_FIX_DISABLE=1` 可以单独关掉。

## 附：截图修复（`libqq-screenshot.so`）

QQ 截图前先执行 `echo $XDG_SESSION_TYPE`：是 `wayland` 就走 GNOME 专用的方式（`dbus-send` 调 `org.gnome.Shell.Screenshot`，或用 `gjs` 跑 `screencast.gjs`），否则用主程序里的 X11 代码对根窗口 `XGetImage` / `XShmGetImage` 截全屏。

启动器为了让屏幕共享不被拦截，给 QQ 的是 `XDG_SESSION_TYPE=x11`，于是 QQ 走 X11 这条。而 Wayland 下的 XWayland 是 rootless 的，根窗口没有内容，`XGetImage` 必然返回 `BadMatch`；Xlib 打印错误后返回 NULL，QQ 不检查就去读像素，段错误，按下截图键瞬间闪退。

本库只拦截对根窗口的截取，别的窗口照常交给 Xlib：

- 在 Wayland 会话里，通过 `wlr-screencopy` 逐个截取 Wayland 输出，按 X 的显示器布局（XRandR monitors，名字与 `wl_output` 的名字对应）拼成根窗口坐标系下的整张画面交给 QQ。不能「X 失败了再截」：`XShmGetImage` 在 rootless XWayland 上不报错，只返回全黑；
- 不在 Wayland 会话里、或合成器不支持 `wlr-screencopy`（KDE、GNOME）时，照常调用 Xlib，但临时接管 X 错误（默认处理会直接退出进程），仍然失败就给一张黑图。真正的 X11 会话里截取会成功，行为不变。

截图之后，QQ 会弹出自己的截图窗口，把整张画面当背景让你框选。这个窗口是按「放在桌面左上角、和整个桌面一样大」设计的，Wayland 下程序无法自己指定窗口位置和大小，平铺式合成器会把它当普通窗口平铺，画面按窗口宽度缩放后重复显示。这一点本库没有处理。
